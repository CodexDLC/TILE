# Область задачи TALE

Сначала различить аудит/объяснение и разрешённое изменение. Аудит не разрешает исправления кода. Использовать глобальное правило полномочий, не требовать повторного согласования уже разрешённой работы.

Кратко определить поверхность, основной пользовательский сценарий и владельца. Затем загрузить только нужное:

- `features.content`: статья, Page, блоки, публикация, поиск по контенту → architecture + page-blocks.
- `features.places`: географические сущности и связь с Page → architecture + page-blocks.
- Авторский кабинет → cabinet-feature-change; публичное чтение → public-template-change.
- Стили/визуальная приёмка/сборка → design-system.
- Контактная форма → фактические `features.contacts` и `features.messaging`, их текущие маршруты и тесты.

Сначала существующий selector/service/component. Новый домен не создавать только ради страницы меню. Не переносить booking, кампании или чужие Lily-правила в TALE.

Наличие будущего требования в `docs/development-plan/01-mvp-stages-and-improvements.md` не означает разрешения реализации. Особенно аудио, оплата, новая схема языков и внешний деплой.

При затронутой библиотеке: источник и её usage-skill → фактический API → проектный адаптер. Если проблема общая, оформить библиотечную задачу, не копировать всю оболочку в проект.
