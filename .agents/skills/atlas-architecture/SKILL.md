# Архитектура TALE

Проверенные владельцы:

- `src/atlas/core`: настройки Django, корневые URL, sitemap, интеграция выполнения.
- `src/atlas/system`: общие настройки сайта, контекст, технический выбор языка.
- `src/atlas/cabinet`: проектная интеграция оболочки, auth и общие кабинетные экраны.
- `src/atlas/features/content`: Page/typed blocks, авторский редактор, чтение и публикация статей.
- `src/atlas/features/places`: Country/Region/City/Place и их связи с Page.
- `src/atlas/features/contacts`, `features/messaging`: маршруты контактов и проектная интеграция сообщений; конкретный обработчик проверять по URL.
- `features.main` содержит старые шаблоны/страницы; не считать их действующим источником публичного сайта без трассировки URL.

Чтение и подготовка контекста принадлежат selectors; запись/транзакции/побочные действия — services. Views разбирают запрос, проверяют доступ, вызывают слои и возвращают ответ. Шаблоны не выполняют доменные решения и запись. Пакеты расширять по ответственности, не создавать классы/абстракции ради формальности.

## Чистая архитектура при развитии проекта

Для обоих рабочих режимов: перед нетривиальным изменением определить ответственность, её владельца и способ проверки. Стремиться к небольшим связным классам и модулям; не накапливать несвязанные обязанности в одном view, сервисе, классе или файле в расчёте на последующую ревизию разработчиком.

- Сначала найти существующий модуль или компонент. Новый файл размещать в соответствующей feature и слое, называть по назначению. Разделять по самостоятельным обязанностям, а не по произвольному лимиту строк; не заводить общие utils/managers для несвязанных задач.
- Для сложного сценария, нескольких зависимостей или собственного состояния предпочитать небольшой класс с явными зависимостями. Для короткого запроса или преобразования без состояния достаточно функции. Не создавать класс, интерфейс или отдельный файл для каждого действия автоматически.
- View отвечает за HTTP и вызов сценария; форма — за разбор и проверку ввода. Сервис координирует запись и транзакции, selector — чтение. Бизнес-правила, которые обязательны для всех путей вызова, проверяются в доменной/сервисной части, а не только в форме или шаблоне.
- Самостоятельные бизнес-правила и вычисления отделять от request, шаблонов и внешних клиентов. Интеграции отделять адаптерами; выделять контракт зависимости там, где есть реальная граница или необходимость подмены. Существующий Django ORM допустим в selectors/services: не вводить повсеместные repositories и дублирующие модели ради схемы архитектуры.
- Если сценарий состоит из разных этапов, оркестратор связывает их, а каждый самостоятельный алгоритм имеет своего владельца. При добавлении новой несвязанной обязанности выделить её, а не расширять «божественный объект».
- Делать локальное разделение в пределах задачи. Переписывание соседних модулей, новая схема данных и изменение библиотечных контрактов не становятся разрешёнными из-за этого правила; граница согласования моделей из atlas-working-modes сохраняется.

Для существенной архитектурной работы применять глобальный hexagonal-oop-architecture, если он доступен. При проверке результата объяснить основные границы и проверить затронутое поведение; для рефакторинга сохранить поведение проверками по реальному риску. Известный оставшийся архитектурный долг обозначать явно, не выдавать его за завершённое разделение и не откладывать всю ответственность на будущее ревью.

При изменении схемы установить владельца модели, проверить migrations, translation.py, формы/admin, selectors/services и существующие данные. `django-modeltranslation` уже владеет языковыми полями; не создавать параллельную систему переводов без отдельного решения. Географическая иерархия не означает обязательную привязку каждой STORY к городу: текущий редактор разрешает самостоятельную статью.

Совместимость по умолчанию требуется для опубликованных URL и существующих данных/блоков. Не переносить данные и не менять зависимости как побочную часть UI-задачи.

Источники по необходимости: `docs/architecture/README.md`, `content-platform.md`, `feature-slice.md`; их проектные планы сверять с текущими models/selectors/services. Инварианты статьи — в page-blocks.

Команды после проверки работоспособного окружения: `uv run --locked --extra dev manage check`, `uv run --locked --extra dev manage makemigrations --check --dry-run`, релевантный pytest. Это не разрешение запускать migrate в рабочей базе. Если editable-пути сломаны после переезда, сначала диагностировать и исправлять в пределах полномочий текущего задания; отдельное согласование требуется только для выхода за его рамки; не заявлять штатный запуск по успешной временной подстановке PYTHONPATH.
