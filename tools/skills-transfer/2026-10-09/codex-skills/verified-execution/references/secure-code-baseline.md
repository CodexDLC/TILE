# Security at changed trust boundaries

Use only sections relevant to the change. This is implementation hygiene, not a full audit or a reason to modify unrelated code. Report serious adjacent findings separately. Add focused negative tests when the boundary warrants them; do not run a complete security suite for every edit.

- **Injection:** parameterize SQL/NoSQL queries; allowlist identifiers that cannot be parameterized. Avoid shell interpretation and dynamic eval. Escape output for its HTML/JS/URL context; HTML sanitization is needed only where rich content is deliberately supported. Never disable template autoescaping for user input. Validate schemas/types/lengths server-side; validation alone does not prevent injection.
- **Access:** authenticate and authorize each protected operation and object on the server, including downloads and exports; scope queries to the current tenant. Client roles, IDs and hidden controls are not authority. Allowlist writable fields against mass assignment. Retain framework CSRF, secure session and password handling.
- **Uploads:** allow only necessary formats; validate actual structure, not just extension, Content-Type or magic bytes. For raster avatars, decode and re-encode into an approved format using maintained libraries, with limits on request bytes, decoded pixels, frames, memory and processing time. Strip unnecessary metadata. Reject malformed files. This reduces risk but cannot prove a parser is invulnerable.
  SVG/HTML and document formats have different active-content risks: reject unless needed, otherwise use a dedicated vetted sanitization/conversion and serving policy. Generate storage names; prevent traversal/overwrite; keep uploads outside executable app paths. Serve with appropriate types, nosniff and access control; isolate untrusted public content on a separate origin where appropriate. Do not publicly expose originals just because a safe preview exists. Scanning is an additional layer, not proof of safety. Use harmless fixtures for validation, never real malware.
- **Outbound requests:** when users control destinations, constrain schemes/hosts and redirects, block internal/link-local/metadata destinations, and use time/size limits. Consider DNS resolution/rebinding and network egress controls; URL regex alone is insufficient.
- **Sensitive operations:** derive prices, permissions and game rewards server-side. Verify payment webhooks with provider-supported signatures on the required original payload, validate event/order/amount/currency, and handle duplicate/reordered delivery transactionally. Do not trust browser payment success redirects.
- **Secrets and failures:** keep credentials out of source, client bundles, URLs and logs; redact findings. Return safe errors; do not invent cryptography or disable TLS verification. Check current primary advisories when a dependency risk is relevant; distinguish vulnerable version from demonstrated exploitability.

Sources (checked 2026-10-08; consult current framework/provider docs when applying): [OWASP file uploads](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html), [injection prevention](https://cheatsheetseries.owasp.org/cheatsheets/Injection_Prevention_Cheat_Sheet.html), [authorization](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html).
